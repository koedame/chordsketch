# 0044. Pre-1.0 releases may break compatibility; the MSRV moves to 1.88

- **Status**: Accepted
- **Date**: 2026-08-31

## Context

The workspace is at `0.5.0` and every crate is bumped in lockstep. The only
statement about pre-1.0 stability lived in one sentence in
`docs/releasing.md` — "While the version is below 1.0.0, minor version bumps
may include breaking changes" — which says nothing about patch bumps, nothing
about the toolchain floor, and does not appear anywhere a consumer of the
crate or the CLI would read it. Nothing in `README.md` told a downstream
reader that the surface is still moving.

That gap turned into a concrete block. Two Dependabot bumps could not merge
because their transitive graph declares a higher Rust floor than the
workspace's `rust-version = "1.85"`:

| PR | Bump | Transitive crate forcing the floor |
|---|---|---|
| [#2758](https://github.com/koedame/chordsketch/pull/2758) | `uniffi` 0.31.2 → 0.32.0 | `askama` 0.16 (`rust-version = 1.88`), `cargo_metadata` 0.23 (`1.86`) |
| [#2750](https://github.com/koedame/chordsketch/pull/2750) | `pdf-extract` 0.10.0 → 0.12.0 | `lopdf` 0.42 / `rand` 0.10 line |

The `Test (…, 1.85.0)` matrix leg failed on both, and with `fail-fast` on,
the `stable` legs were cancelled behind it — so the whole rollup was red.

Ecosystem crates now move their declared `rust-version` forward on a roughly
six-month cadence. Holding 1.85 does not keep the crate reachable by more
users; it keeps the crate *behind*, and it accumulates as a permanently red
Dependabot queue, because `open-pull-requests-limit` (5) means unmergeable PRs
crowd out the ones that would merge cleanly.

The question this ADR settles is not "should we take 1.88" in isolation. It is
whether an MSRV raise is a breaking change that must wait for `1.0.0`. Under
the strictest reading of Semantic Versioning it is; under that reading the
project would carry an ecosystem-lagging toolchain floor for the entire
validation phase.

## Decision

**Pre-1.0, any release may break compatibility, and an MSRV raise is not held
back for `1.0.0`.**

1. Until `1.0.0` ships, a `0.x` bump — minor *or* patch — may rename or remove
   public items, change rendered output / CLI flags / config keys / directive
   semantics, change the WASM / NAPI / FFI wire shape, and raise the minimum
   supported Rust version. No deprecation cycle and no compatibility shim is
   owed across the break.
2. Breaking changes are still *documented*: the CHANGELOG names them, and one
   large enough to need steps gets a guide under `docs/migration/`. The
   freedom is to make the change, not to make it silently.
3. The policy is stated where consumers read it — a `## Stability` section in
   `README.md` linking to the full text in `docs/releasing.md` — not only in
   the release runbook.
4. **The workspace MSRV moves `1.85` → `1.88`** under this policy. `1.88` is
   the highest floor declared by anything in the two blocked bumps' graphs
   (`askama` 0.16); nothing in the workspace needs more.
5. From `1.0.0` onward the normal Semantic Versioning contract applies and
   breaking changes wait for a major bump.

## Rationale

**The validation phase is the reason the version is still `0.x`.** The formats,
the API surface, and the toolchain floor are being proven against real
ChordPro / iReal Pro material. A project that will not break its own surface
during that phase is not validating anything — it is shipping `1.0.0`
semantics without the `1.0.0` number.

**A blanket "no MSRV raise" is enforced by the dependency graph, not by us.**
The floor is set by whichever transitive crate declares the highest
`rust-version`. Refusing to move means refusing the bump, which means the
advisory-relevant updates behind it also do not land — and with a 5-PR
Dependabot cap, one stuck PR blocks four others. The stability that a frozen
MSRV buys is paid for in unpatched dependencies.

**1.88 rather than "whatever stable is."** The MSRV is a floor for consumers,
not a convenience for this repo. It moves to the lowest version that unblocks
the work in hand and no further, and CI keeps a dedicated `1.88.0` matrix leg
so the floor stays a tested claim rather than a comment.

**Nix is unaffected.** The pinned `nixpkgs` (nixos-unstable 2026-05-23) ships
Rust 1.95, so `nix build .#chordsketch` clears 1.88 with room.

## Consequences

- `Cargo.toml`'s `rust-version`, the `ci.yml` test matrix, `README.md`,
  `CONTRIBUTING.md`, `docs/dev-setup.md`, `apps/desktop/README.md`, and
  `flake.nix`'s toolchain comments all state 1.88. They are expected to move
  again, together, the next time a bump forces it.
- Consumers on 1.85–1.87 stay on the last `0.5.x` release that supported
  them. This is the cost the policy accepts.
- **Raising the MSRV turns lints on, not just the compiler floor.** Clippy
  gates suggestions on `rust-version`, so declaring 1.88 made
  `clippy::collapsible_if` start proposing let-chains (`if let x = y && cond`,
  stable in 1.88) and, with `-D warnings`, fail CI at ~50 sites across nine
  crates. The sites were collapsed rather than silenced — an MSRV move should
  be budgeted as "floor plus whatever lints the floor unlocks", and the fix
  belongs in the same PR as the bump, because the repository has no green
  intermediate state between the two.
- **`main`'s branch protection names the matrix legs by version**
  (`Test (ubuntu-latest, 1.85.0)` and its macOS / Windows siblings are
  required contexts). Renaming the leg makes the old contexts report
  forever-pending, so every MSRV move is two edits: the matrix, and the
  `required_status_checks.contexts` list. They are updated together, with
  the protection edit landing while the MSRV PR is in flight — otherwise
  the PR that renames the leg can never satisfy its own gate.
- `crates/render-ireal`'s `resvg` pin note is now wrong about its own
  blocker: with the floor at 1.88, `resvg` 0.46 / 0.47 (`rust-version`
  1.87) are reachable, and what actually holds the line at 0.45 is
  `svg2pdf` 0.13's `usvg ^0.45` requirement. The comment says so now.
  [ADR-0014](0014-bravura-glyphs-as-svg-paths.md) records the older
  MSRV-blocked framing as it stood at the time and is left unedited.
- The `## Stability` section is one more README block that has to stay true;
  `readme-sync.md` does not cover it (it adds no install or usage command, and
  the committed command snapshot is unchanged), so it falls under ordinary
  doc maintenance.

## Alternatives considered

**Hold 1.85 and close the two PRs.** Cheapest today. It leaves `uniffi` — the
crate that generates every non-Rust binding — five months stale, and the next
bump that touches the same graph fails identically. It also does not stop the
floor from rising; it only stops us from noticing.

**Hold 1.85 and pin the transitive crates down.** `askama` and `cargo_metadata`
arrive through `uniffi_bindgen`; pinning them means pinning `uniffi` itself,
which is the bump. Not available.

**Raise to current stable (1.98).** Removes the problem for longer and costs
nothing internally, but sets a consumer-facing floor far above what any
dependency actually needs. Rejected: the MSRV is a promise to downstream, and
raising it further than required spends that promise for no gain.

**Treat the MSRV raise as requiring `1.0.0`.** The strict-SemVer reading. It
makes the validation phase strictly more expensive than the stable phase would
be, which inverts what `0.x` is for.
