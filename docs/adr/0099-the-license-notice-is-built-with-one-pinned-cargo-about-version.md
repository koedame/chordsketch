# 0099. The license notice is built with one pinned cargo-about version

- **Status**: Accepted
- **Date**: 2026-11-24
- **Amends**: [ADR-0089](0089-dependabot-cargo-updates-get-their-license-notice-regenerated-by-a-workflow.md)

## Context

`THIRD_PARTY_LICENSES.md` is generated by `scripts/third-party-licenses.py`,
which asks `cargo-about` for the license texts of every crate
([ADR-0085](0085-binaries-ship-a-generated-third-party-license-notice.md)).
It is regenerated in two places: on a contributor's machine, and by
`dependabot-licenses.yml` on Dependabot's cargo PRs
([ADR-0089](0089-dependabot-cargo-updates-get-their-license-notice-regenerated-by-a-workflow.md)).

Neither place said which `cargo-about`. ADR-0089 recorded that as harmless:
"`cargo-about` is installed unpinned, as `cargo-audit` is. The check compares
hashes of the inputs, not the rendered text, so a different `cargo-about`
release cannot make the check fail." The second sentence is the problem, not
a reassurance. Two releases do not produce the same notice from the same
`Cargo.lock`. Measured on the lock file of `main` at `ae5b92f7`:

| `cargo-about` | License sections for Rust crates | ISC sections for `ring 0.17.14` |
|---|---|---|
| 0.9.2 | 156 | 17 |
| 0.9.3 | 161 | 22 |

`ring` carries several ISC texts with different copyright holders, and 0.9.2
misses five of them. Both files pass `--check`, because the input hash covers
the lock files and the script and the body hash only says the file was not
edited by hand. So whichever version happened to be installed decided
whether five copyright notices were shipped, the diff showed it only as a few
hundred changed lines in a generated file, and no check could notice. The
versions do drift apart: `cargo install cargo-about` takes the newest release,
while `taiki-e/install-action` with a bare tool name takes the newest release
the pinned action commit knows about.

ISC, like MIT and the BSD licenses, requires the copyright notice to be kept
in copies of the software. A notice that silently loses sections is the
failure the file exists to prevent.

## Decision

1. **The notice is built with exactly one `cargo-about` version.** It is
   written in one place, the `tool: cargo-about@<version>` line of
   `.github/actions/install-cargo-about/action.yml`
   (the tool-version convention of `.claude/rules/ci-parallelization.md`).
2. **`dependabot-licenses.yml` installs `cargo-about` through that composite
   action**, and no workflow or action installs it any other way.
3. **`scripts/third-party-licenses.py` reads the version from the composite
   action and refuses to regenerate with any other.** It runs
   `cargo about --version` first and stops, before `npm ci` or anything else,
   with the `cargo install cargo-about --locked --version <version>` command
   to run. A missing `cargo-about` gets the same message.
4. **The pinned version is one of the inputs `--check` hashes.** Moving the
   pin without regenerating fails CI. Other edits to the composite action (a
   new `install-action` commit) do not change the hash.
5. **`--check` itself does not look at the installed `cargo-about`.** It
   never runs it, and it has to keep working in the jobs that have no Rust
   toolchain.
6. **The pin is 0.9.3**, the version that reproduces the committed notice
   byte for byte and the newest release at the time of writing. Moving it is
   a deliberate change: regenerate with the new version and compare the
   number of sections per license before and after; a release that finds
   fewer texts is not adopted until the missing ones are accounted for.

## Rationale

- The file's content depends on the tool version, so the tool version is an
  input like the lock files are, and inputs are hashed.
- Checking the version in the script, rather than only pinning it in the
  workflow, covers the contributor's machine, which is where most
  regenerations happen (every PR that changes a lock file outside
  Dependabot).
- One location for the version follows the existing rule for `wasm-pack`
  and `macports-base`. The script reading the composite action, instead of
  the action reading the script, keeps the composite a plain
  `install-action` call that Dependabot can maintain.

## Consequences

- A new `cargo-about` release is not picked up until someone moves the pin.
  A fix for a wrongly detected license therefore waits for that change.
  Mitigation: the change is one line plus a regeneration, and the section
  comparison in Decision 6 shows what the release changes.
- Regenerating locally needs the pinned version installed, not just any.
  The script prints the exact command.
- `install-action` downloads only the releases its pinned commit lists. A
  pin newer than that commit knows falls back to `cargo-binstall`; bump the
  action commit first.
- `dependabot-licenses.yml` reads the composite action from the pull request
  branch (a local action resolves in the checked-out tree). Its first step
  already rejects a pull request that changes anything but Cargo manifests
  and the lock file, so the action it runs is the one on `main`.
- Nothing counts sections. The guarantee is that the same lock files and the
  same tool version give the same notice, and that a different tool version
  cannot be used unnoticed.

## Alternatives considered

- **Pin only in the workflow.** Leaves local regenerations on whatever is
  installed, which is the side that produced the larger file in the first
  place.
- **Keep the version in the script and have the workflow read it.** A
  second convention next to the composite actions for `wasm-pack` and
  `macports-base`, and a workflow step that parses Python.
- **Make `--check` regenerate and compare the text.** It would catch any
  difference, but needs the Rust toolchain, network access and four `npm ci`
  runs in a job that today needs none of them (ADR-0085 chose the hash check
  for that reason).
- **Assert a minimum number of sections per crate.** The numbers change
  with every dependency update, so the floor would be edited routinely and
  stop meaning anything.
